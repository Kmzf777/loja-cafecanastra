# Onda 1C — Infra F7: empacotamento, proxy, backup, CI e runbook

> Plano detalhado da Onda 1C do plano mestre
> `docs/superpowers/plans/2026-08-20-plano-mestre-pendencias.md`.
> Território: arquivos NOVOS em `deploy/`, `scripts/`, `.github/`,
> `docs/deploy.md`, `backend/Dockerfile`, `frontend/Dockerfile`, os
> `.dockerignore`s, e UMA linha em `frontend/next.config.mjs`
> (`output: "standalone"`). Nada mais é tocado. Sem commit.

**Goal:** a loja passa a ter caminho de produção completo: imagem Docker dos
dois lados, compose de produção com nginx na frente (vitrine e API na MESMA
origem, API sob `/api/*` — `docs/producao.md` §2), alternativa PM2 sem Docker,
backup agendável com cópia para fora da VPS (§5.6), CI que roda as duas suítes
e o build, e um runbook que uma pessoa cuidadosa segue sem conhecer o repo.

---

## Fatos levantados antes de escrever (mudam o desenho)

1. **O build do frontend importa arquivo de FORA de `frontend/`**:
   `frontend/lib/catalogo/produtos.ts` faz
   `import bruto from "../../../data/catalogo-canastra.json"` — o JSON vive na
   raiz do repositório. Consequência: **o contexto de build Docker do frontend
   não pode ser `frontend/`; tem de ser a raiz do repo**, copiando `frontend/`
   e `data/`. O webpack embute o JSON no bundle em build-time, então o runtime
   standalone não precisa do arquivo — mas o build precisa dele no contexto.
   Por isso os dois `.dockerignore` são: `backend/.dockerignore` (contexto
   `backend/`) e `.dockerignore` na raiz (contexto do frontend).
2. **`outputFileTracingRoot: import.meta.dirname` já está no `next.config.mjs`**
   e aponta para `frontend/` — ou seja, o Next NÃO trata o repo como monorepo
   para fins de tracing. A previsão é o standalone sair em
   `frontend/.next/standalone/server.js` (SEM o subdiretório `frontend/` que um
   tracing root na raiz criaria). O build local desta onda **confirma** o
   caminho real e o `ecosystem.config.cjs` + runbook registram o que saiu.
3. **`backend/src/index.js` carrega dotenv de `./src/.env` relativo ao cwd** —
   o processo TEM de subir com cwd = `backend/` (PM2: `cwd`; Docker: WORKDIR
   `/app` com `src/` dentro; num container o arquivo nem existe e o dotenv
   silencia — as variáveis vêm do `env_file` do compose).
4. **`db:migrar` NÃO lê `.env` nenhum** (exige `DATABASE_URL` exportada);
   `db:seed` lê `backend/src/.env` sozinho e precisa de
   `data/catalogo-canastra.json` na raiz do repo. Logo: migração e seed rodam
   **do clone na VPS**, não de dentro da imagem (a imagem do backend leva `db/`
   mesmo assim — `docker compose exec api node db/migrar.js` funciona; o seed
   não, por causa do `data/`, e o runbook diz isso).
5. **Lockfiles em dia**: `backend/package-lock.json` e
   `frontend/package-lock.json` estão sincronizados com os respectivos
   `package.json` (conferido por script) — CI usa `npm ci` nos dois.
6. **Docker NÃO está disponível nesta máquina Windows** (`docker` não é
   reconhecido). O `docker build` fica como verificação pendente; o que se
   valida aqui é: build standalone do Next (uma vez, de verdade), sintaxe YAML
   dos dois arquivos (parse com o pacote `yaml`/`js-yaml` de `node_modules` ou
   revisão linha a linha), sintaxe do `ecosystem.config.cjs` (`node --check`) e
   do `backup-banco.sh` (`bash -n`).
7. **Uploads do painel vão para o Cloudinary** (`backend/src/middleware/multer.js`);
   `/uploads` estático é legado. Ainda assim o compose monta volume nomeado em
   `/app/uploads` — custo zero, e um arquivo local não some num restart.
8. **`NEXT_PUBLIC_API_URL=/api` funciona no código atual**: `API_BASE` só faz
   `.replace(/\/$/, "")` e os `fetch` viram relativos à origem — exatamente o
   que a topologia §2 quer. No CSP um source `/api` é ignorado pelo navegador,
   mas `'self'` já cobre a mesma origem; sem efeito colateral.
9. **Limite de upload**: multer aceita até 5 MB por arquivo e 2 arquivos —
   `client_max_body_size 6m` no nginx cobre 1 imagem de 5 MB + overhead de
   multipart (o formulário de config manda 2 banners; se um dia os dois vierem
   no teto, o ajuste é uma linha e o conf diz onde).

## Entregas, na ordem de execução

1. `frontend/next.config.mjs` — acrescentar `output: "standalone"` ao
   `nextConfig`, com comentário curto. Única mudança no arquivo.
2. Disparar `npm --prefix frontend run build` (em background, timeout longo) —
   prova que o standalone não quebra e revela o caminho real do `server.js`.
3. `backend/.dockerignore` e `.dockerignore` (raiz).
4. `backend/Dockerfile` — `node:22-bookworm-slim`, 2 estágios (deps com
   `npm ci --omit=dev`; runtime com `NODE_ENV=production`, usuário `node`,
   `src/` + `db/`, diretório `uploads/` gravável, `EXPOSE 3333`, HEALTHCHECK
   `node -e` com `fetch` em `/health`, `CMD ["node","src/index.js"]`).
5. `frontend/Dockerfile` — contexto = raiz do repo; estágios deps → build →
   runtime. `ARG`/`ENV` das `NEXT_PUBLIC_*` (SUPABASE_URL, SUPABASE_ANON_KEY,
   SITE_URL, API_URL=/api, e as três futuras do plano mestre — MP_PUBLIC_KEY,
   GA4_ID, WHATSAPP — opcionais e vazias), documentando que `NEXT_PUBLIC_*` é
   assada em BUILD-time. Runtime: usuário `node`, copia `.next/standalone`,
   `.next/static`, `public`, `PORT=3000`, `HOSTNAME=0.0.0.0`, HEALTHCHECK na
   raiz, `CMD ["node","server.js"]` (caminho ajustado ao que o build provar).
6. `deploy/docker-compose.prod.yml` — serviços `api` (env_file
   `../backend/src/.env`, `NODE_ENV=production` forçado por `environment`,
   expose 3333, volume de uploads), `web` (build args das `NEXT_PUBLIC_*` via
   substituição do `deploy/.env`, expose 3000), `nginx` (80/443, confs e
   certificados montados, depends_on), rede interna, `restart: unless-stopped`,
   SEM banco. Acesso ao Supabase da VPS documentado nas DUAS formas:
   `host.docker.internal` + `extra_hosts: host-gateway`, OU rede externa do
   compose do Supabase (bloco comentado).
7. `deploy/nginx/loja.conf` — 80→443 (com webroot do certbot comentado), 443
   com TLS montado, `location /api/ { proxy_pass http://api:3333/; }` (remove o
   prefixo), `location / { proxy_pass http://web:3000; }` com upgrade de
   websocket, `X-Forwarded-*`, gzip, `client_max_body_size 6m`, comentários de
   onde entra o certbot, bloco comentado do domínio do Supabase/Kong e a troca
   `api:3333`/`web:3000` → `127.0.0.1` para o caminho PM2 sem Docker.
8. `deploy/ecosystem.config.cjs` — PM2: `canastra-api` (cwd `backend/`, script
   `src/index.js`, `NODE_ENV=production`, `max_memory_restart`, logs com data)
   e `canastra-web` (cwd no diretório standalone REAL confirmado pelo build,
   script `server.js`, `PORT`, `HOSTNAME=127.0.0.1` porque o nginx está na
   mesma máquina). Caminhos por `path.join(__dirname, "..")` — o repo vive
   onde for clonado.
9. `scripts/backup-banco.sh` — `set -euo pipefail`; `pg_dump -Fc` via
   `DATABASE_URL` | gzip; nome `canastra-AAAAMMDD-HHMMSS.dump.gz`; escreve em
   arquivo temporário e move no fim (backup pela metade não fica com nome de
   backup); **verificação embutida**: `gunzip -c | pg_restore --list` antes de
   aceitar; retenção `RETENCAO_DIAS` (padrão 14) por `find -mtime -delete`;
   destino `BACKUP_DIR` configurável; bloco rclone comentado (cópia para FORA
   da VPS — §5.6); restauração completa documentada em comentário.
   + `scripts/backup-banco.cron.exemplo` com a linha diária das 03h.
10. `.github/workflows/ci.yml` — push/PR para `main` e `feat/**`; job único
    Ubuntu, Node 22 com cache npm dos dois lockfiles; `npm ci` dos dois lados,
    `npm --prefix backend test` (embedded-postgres baixa binário Linux via
    optional dep — roda como usuário `runner`, não root), `npm --prefix
    frontend run test`, `npm --prefix frontend run build` com `NEXT_PUBLIC_*`
    dummy de CI.
11. `docs/deploy.md` — runbook VPS do zero: pré-requisitos; clone; `.env` dos
    dois lados (apontando para os `.env.example`); `PGRST_DB_SCHEMAS` com
    `canastra` + restart do PostgREST (§3.3); os 3 ajustes manuais do GoTrue
    (§3.5); `db:setup`; subir por compose OU PM2+nginx (com os passos de cópia
    do standalone); webhook do MP com a URL pública `/api/webhook/mercadopago`;
    domínio verificado no Resend; agendar backup; checklist pós-deploy
    reaproveitando a §8 do `docs/producao.md`.
12. Verificações finais: parse YAML dos dois arquivos, `node --check` no
    ecosystem, `bash -n` no script de backup, resultado do build standalone e
    caminho real do `server.js` refletido em 5/8/11.

## O que esta máquina não prova (e quem prova)

- `docker build`/`docker compose config` — sem Docker aqui. O CI cobre build e
  testes de código; os Dockerfiles ficam como pendência de primeira execução na
  VPS (o runbook manda `docker compose build` antes de `up`, então a falha
  apareceria no primeiro passo, não com a loja no ar).
- nginx `-t` — validação de sintaxe do conf fica para a VPS
  (`docker compose exec nginx nginx -t`, escrito no runbook).
- O cron e o rclone — dependem da VPS e de credencial de storage remoto.
